# 项目版本管理

本项目使用一个 GitHub 仓库连续开发五代机器人系统。五代不是五份互不相关的代码副本，而是同一套代码逐代升级后的五个永久快照。

## 核心规则

1. `main` 保存最新完成并通过验收的稳定版本。
2. 每一代开始时创建一个独立开发分支。
3. 每个小功能在该代开发分支上形成清晰提交。
4. 当前代全部功能、测试和文档完成后，通过 Pull Request 合并到 `main`。
5. 合并完成后创建永久 Git Tag 和 GitHub Release。
6. 未完成的版本不提前创建正式标签，避免把开发中代码误认为稳定版本。

## 分支、标签与 Release

| Git 对象 | 用途 | 是否持续变化 |
| --- | --- | --- |
| `main` | 最新稳定版本 | 只在一代完成后更新 |
| 开发分支 | 当前代的学习、实现和测试 | 开发期间持续更新 |
| Git Tag | 某一代最终代码的永久书签 | 创建后不修改 |
| GitHub Release | 版本介绍、截图、发布说明和下载入口 | 发布后只修正文案 |

## 每一代的操作顺序

```text
从稳定 main 创建当前代开发分支
→ 按小课程实现功能并提交
→ 持续运行测试和更新文档
→ 完成该代最终验收
→ Pull Request 合并到 main
→ 创建 vX.0.0 Tag
→ 创建 GitHub Release
→ 从新的稳定 main 开始下一代
```

## 为什么不复制五个版本文件夹

如果把每一代复制成 `version1/`、`version2/` 等目录，旧代码会大量重复。修复基础算法时需要同步修改多份文件，Python 包和测试路径也会越来越混乱。

Git Tag 已经可以完整保存每一代当时的代码、测试、README 和示例，因此不需要复制源代码目录。用户可以在 GitHub 的分支菜单中选择 `Tags`，随时查看或下载任意已发布版本。

## 稳定性保证

- 后续开发不会改变 `v1.0.0` 指向的代码。
- V2.0 开发期间，`main` 继续作为稳定基线。
- 只有全部 V2.0 验收标准完成后，才创建 `v2.0.0`。
- V3.0、V4.0 和 V5.0 也遵守同样流程。
